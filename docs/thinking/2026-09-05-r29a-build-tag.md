# R2.9a — moving the `B_bootstrap` instrument behind a build tag

**Date:** 2026-09-05 · **Seat:** BUILDER (deliberation → build) · **Status:** BUILT 2026-09-05 on
branch `builder/r2.9a-build-tag` (no PR); §7 records the build as it landed.

**Binding input.** `D-BB-BUILD-TAG` (`docs/decisions.md`), ratified by the owner 2026-09-05
(*"I'll take your recommendation, proceed"*). Overriding: `docs/TENETS.md` Part VI Don't #3 and
Part IX; `docs/build-process.md`. Four seat reports and two certifications are cited in full in the
decision entry and are not repeated here.

**Scope, stated as a refusal.** This changes WHERE the instrument compiles and WHEN it records. It
changes nothing about WHAT it measures. Not touched: the histogram bins, the axis edges, the
minimum-requester floor value or its derivation, the two-clock design, `W`, `q`, the population `P`,
the tail-merge of low-count cells (with the Researcher), the per-object durability surface,
status-snapshot caching.

## 1. The mechanism, in one paragraph

The failure is that a default silt binary contains a who-fetches-what recording mechanism, because
`cmd/silt/daemon.go:673` called `ledger.SetObservabilityClock(clk, …)` unconditionally — with a
comment saying this was deliberate, so that flipping `-bbootstrap` on at the next restart would find
an already-stamped population. `-bbootstrap` set exactly one field, `uiServer.bBootstrap`, which
gated the RENDERING. So on every default-flags node the ledger held
`(identity, cumulative bytes, first-seen wall-clock nanosecond)` per requester, and no flag disabled
it; the red-team demonstrated recovery of arrival ORDER and GAP from two accounts' stamps alone
(`TestRT_BB4_TheStampIsRecordedRegardlessOfTheFlag`). Part VI Don't #3 is a rule about what silt
*builds*, so a binary that holds the capability and declines to print it is the thing the rule
forbids. This change addresses it by compiling the instrument only under a build tag — no histogram
type, no census reader, no age stamping, no flag in a default binary — and, inside a tagged build,
by making the injection conditional on the flag, so the recording is gated where only the rendering
was.

## 2. Option set — tag granularity

The instrument spans three packages: `core/credit` (the census + the histogram), `core/node` (the
seam), `cmd/silt` (the flag + the renderer).

| Option | Cost | Benefit |
|---|---|---|
| **A. ONE tag across all three packages** *(chosen)* | One name to know; a partial build is impossible, so you cannot compile "half" of it | The mechanism is one mechanism. A default binary loses all of it at once, and the claim in the decision entry is a single sentence a reviewer can check with one `go tool nm` |
| B. A tag per package (`bbcredit` / `bbnode` / `bbui`) | Three names, six files of stubs, and 2³ build configurations of which 6 are meaningless | Would let someone compile the census without the endpoint — which is *worse*, not better: the recording is the half Don't #3 is about, and this option makes recording-without-publishing a supported build |
| C. No tag; a runtime `-record-bbootstrap` in addition to `-bbootstrap` | Cheapest diff | Refuted by the decision's own premise. Two flags still ship the mechanism, and the bright line is about the artifact |

**Decision: A.** B optimises for a configuration nobody wants and makes the worst one buildable. C
does not answer the question that was asked.

## 3. Option set — the tag NAME

| Candidate | Why not / why |
|---|---|
| **`bbootstrap`** *(chosen)* | It is the exact string of the flag (`-bbootstrap`), the ROADMAP Rock (R2.9a `B_bootstrap`), every source file name and every test name already in the tree. One `grep -ri bbootstrap` finds the tag, the flag, the files, the CI job, the decision and the ROADMAP line together |
| `surveil` / `requestercensus` | More self-indicting, and there is a real argument for a name that states what the code does. Rejected because it introduces an ALIAS: a reader who greps the obvious word finds the code but not the tag, or vice versa, and the two drift |
| `siltobs`, `debug`, `metrics` | Too broad. A tag that reads as "diagnostics" is a tag someone will add unrelated code to, and then a default build loses that too — or, worse, someone enables it for the unrelated code and gets this |

**Decision: `bbootstrap`.** The value of a self-describing name is real but smaller than the value of
one greppable token; the file's own header states what it is, in the place a reader lands.

## 4. Option set — the untagged stub surface

A build tag cannot split a struct's fields, delete a member from a composite literal, or remove a
call from an untagged function. Those three limits, not taste, decide what has to stay. Each site
was resolved by preferring removal, then a zero-cost type, then a function.

| Site | Options | Chosen, and why |
|---|---|---|
| `core/node.Node.BBootstrap` | (i) untagged stub returning `(zero, false)`; (ii) tag the whole file | **(ii), removal.** Its only caller is `cmd/silt`'s renderer, which is tagged the same way, so there is no untagged reference to satisfy. Zero stub |
| `credit.Ledger`'s four `obs*` fields | (i) leave them untagged and nil forever; (ii) collapse into one field whose TYPE is tagged | **(ii).** Leaving them costs 40 bytes on every ledger and leaves `ports.Clock`-shaped state in a binary that has no way to fill it. `bbootstrapState` is `struct{}` untagged (measured: `reflect.Size() == 0`) and holds the two sources under the tag |
| `credit.Register`'s `stampFirstTouch` call | (i) untagged no-op method; (ii) move the call behind a tagged wrapper | **(i).** `Register` is untagged and must stay so; an empty body inlines away. This is the one stub I could not remove, and it is one line |
| `cmd/silt` status payload | (i) `BBootstrap any` field + `omitempty`; (ii) marshal then splice JSON in the tagged build; (iii) an EMBEDDED `statusExtras` struct, empty untagged | **(iii).** (i) leaves the JSON key name `bBootstrap` as a struct-tag string literal in every default binary; (ii) is byte surgery on a payload BB-20 asserts on. (iii) costs one embedded type: `encoding/json` promotes an embedded unexported struct's exported fields, and an empty one promotes nothing, so a default binary carries no key name at all (measured against a control: identical output) |
| `cmd/silt` flag + injection + UI wiring | (i) package-level flag var; (ii) three seam functions with tagged/untagged twins | **(ii).** A package-level flag pointer is process-global and two daemons in one process share it. `registerBBootstrapFlag` returns a closure instead. The three take identical arguments in both builds so the call sites cannot drift |

**The whole untagged surface, as built:** `credit.bbootstrapState` (empty), `credit.stampFirstTouch`
(empty), `main.statusExtras` (empty), `main.registerBBootstrapFlag` (declares nothing),
`main.bbootstrapInject` (injects nothing), `main.bbootstrapWireUI` (wires nothing). Two empty types
and four empty bodies, in two files that document why each survives.

## 5. The trade being reversed, priced

Gating the injection costs the property that flipping the flag yields an already-stamped
population. Stated as the operator's cost: a **restart plus a wait** for the population to re-stamp,
instead of a flag flip.

It is affordable because the wait is **already the run's own precondition**. G-BB-15 requires
monotone uptime ≥ 2× the read bucket's upper edge — 14 days with no restart at `W = 24 h` on the
shipped edges — so the run could never have used a population stamped by an earlier boot anyway; the
ages are boot-relative and a restart destroys every account (R-BB-CENSORED-WINDOW). The old
property's value was therefore always smaller than its comment implied. Against it: an unconditional
injection makes "silt records no first-seen time for a fetcher" false on **every node in the
network**, forever, to save one restart on **one node, once**.

The half-stamped population is refused rather than fitted:
`BBootstrapRunPrecondition` voids a run carrying any unstamped account, and
`TestR29aFlippingTheFlagOnDoesNotRecoverThePastIsTheACCEPTEDCOST` pins that, so the cost is a delay
and never a silently wrong series.

## 6. Why CI must compile the tagged variant

A build tag CI never compiles is code that rots and is broken silently by the next refactor. Five
gate families now run ONLY under the tag — the minimum-requester floor, the G-BB-11′
construct-from-the-instrument-class property, BB-20's wire equivalence, the two-clock cross-check,
and the package-scope export gate. Measured: `go test -run R29a -v` on the three packages reports
**41** top-level PASSes tagged and **7** untagged. Without a tagged job, 34 gates would stop running
the day this merges.

A green `go test -tags bbootstrap ./...` is not sufficient evidence on its own: `-run` with zero
matches exits 0, and a `t.Skip` is also a pass. The job therefore asserts **twelve named anchors
PASSED** — one per surviving gate family, plus both new ones — and fails on any `--- SKIP`.

## 8. What I did NOT build, and why

- **The tail-merge of low-count cells.** It changes a certified shape; it is with the Researcher.
- **A loopback bind check / a `RemoteAddr` gate.** G-BB-12′ and G-BB-13′ Part A are the owner's, and
  the red-team's F5/F11 show the existing `Host` guard is not that boundary. The tag narrows the
  question to tagged builds; it does not answer it.
- **Anything about F2.** Object-level attribution joins `stats.bytesServed` and
  `durability.objects[].funded`, both published unconditionally, both predating R2.9a. It is a
  larger, older surface and it needs its own decision.

## 9. Where I would push back on the instruction

One place. The instruction asks for evidence that "an untagged binary contains no part of the
mechanism". The strongest honest form of that claim is the symbol table plus the flag surface, both
above. It is NOT "the string `bbootstrap` does not appear in the binary" — §7's residual is why. I
built the CI gate on symbols and the flag rather than on `strings`, because a `strings`-based gate
would have to carry an allow-list from day one, and an allow-list is the shape the min-R floor
re-certification already refuted once this week.

### 10.1 Blocker 1 — a guard against a default-build defect, living in the tagged build

**The mechanism.** `TestR29aDaemonDefaultsTheInstrumentOff` asserted that the untagged `daemon.go`
declares no `-bbootstrap`. The file it lives in carries `//go:build bbootstrap`. So the assertion
ran only in the build that cannot have the defect. The reviewer demonstrated it: adding
`_ = fs.Bool("bbootstrap", false, …)` to the untagged `daemon.go` produced a default binary that
**declared and accepted** the flag, with every required check green.

**Why the sibling gate did not catch it.** `TestR29aDefaultBuildHasNoBBootstrapFlag` is untagged,
but it built its own `flag.FlagSet` and called only `registerBBootstrapFlag`. It observed the seam,
never the daemon's own flag set.

**What I could not do, and what I did instead.** `cmdDaemon` builds its `FlagSet` inline with
`flag.ExitOnError`, so no in-process test can parse it — a bad flag exits the test binary. Extracting
a flag-registration factory out of a ~90-line inline block is a real refactor of the daemon's entry
point, for one gate, and I judged that a worse trade than the alternative. The closest observation
available without it is the **default build's own file set**: `go/build` with no tags applied gives
exactly the files `go build` compiles (`bbootstrap_off.go` in, `bbootstrap.go` out — the test asserts
both), and each is AST-parsed for any stdlib-`flag` declaration whose name contains `bbootstrap`,
across `Bool`/`String`/`Duration`/…/`Var` forms. That is strictly stronger than the literal it
replaces: it is not scoped to one file and not scoped to one flag type.

Two controlled reverts, both RED, both reverted:

| # | Revert | Result (untagged, the REQUIRED job) |
|---|---|---|
| b | the reviewer's own: `fs.Bool("bbootstrap", false, …)` in the untagged `daemon.go` | RED — and the built binary accepted `-bbootstrap`, so the gate and the defect agree |
| b2 | a RENAMED reintroduction in a DIFFERENT untagged file: `fs.StringVar(…, "bbootstrap-rows", …)` in `bbootstrap_off.go` | RED |

**What stays tagged, and why.** I moved the assertions whose SUBJECT is the default build. The rest
of `TestR29aDaemonDefaultsTheInstrumentOff` — that `cmd/silt/bbootstrap.go` declares the flag with a
`false` default — is a statement about the TAGGED build's flag semantics and is meaningless in a
build that has no flag. `TestR29aDaemonInjectsBothClocksBeforeTheLedgerIsReachable` is the same case:
in a default build `bbootstrapInject` is an empty function, so the injection ORDER it anchors has no
subject. Everything else tagged asserts on runtime behaviour of types that do not exist untagged.

**The bound I am stating rather than papering over.** This is a NAME-scoped gate. A default-build
reintroduction under a flag name that does not contain `bbootstrap` evades it, exactly as the ruling's
§7 says of the CI symbol check. The complete form of this claim is the linked binary
(`daemon -bbootstrap` must be rejected), which is a CI step, not a Go test — and it is in the job the
owner is making a required check.

### 10.2 Blocker 2 — an exemption justified by a fact that is backwards

**The mechanism.** Four sites justified leaving `account.firstSeenTick`'s surviving writer alone by
saying `RecordBondChallenge` is stamped "from the bond auditor's own request counter rather than
from a wall clock". I read the chain end to end myself rather than take the ruling's word for it:
`core/node/bondaudit.go:143` and `:157` both compute `uint64(n.clock.Now()) + 1`; `:179` records the
node's own bond and `:234` records every peer that answers; `cmd/silt/daemon.go` builds
`clk := walltime.New(loop)` and passes that same `clk` to `node.New`; `adapters/walltime` returns
`time.Now().UnixNano()`. It is a wall clock.

**Where the error came from.** The doc comment on `RecordBondChallenge` in `core/credit/credit.go`
said *"tick is a monotonic counter (the auditor's request clock, exactly like the PoR nonce in
por.go)"*. `por.go`'s `n.rid` **is** a counter; the bond tick is not, and the two were fused in one
sentence. That comment is the apparent source of all four repetitions, so it is corrected at the
source — otherwise the next reader inherits it a third time.

**The residual, disclosed.** Filed as **`R-BB-BOND-STAMP-TUPLE`**, open. On a `-validator` node
(`StartBondAudit` is gated on `*validator`) the auditor stamps a wall-clock nanosecond for the
node's own id and for every peer in `n.peerBonds` that answers a challenge — a set populated only
from non-ephemeral peers advertising a bond root, so it is bonded peers and not the fetcher
population. An identity that is both a bonded peer and a fetcher therefore carries the whole
`(identity, cumulative fetched bytes, first-seen wall-clock nanosecond)` tuple in a **default**
build. The reviewer measured it live at `aged = 1, unstamped = 34`. So the tag's claim holds on the
SERVE path, for the general requester population — which is what the tag and the flag actually
changed — and it does not hold for bonded validator peers.

**What I did NOT do.** `RecordBondChallenge`, `DecayStale` and standing retention are untouched.
That surface is research-gated and routed separately. The job here was to make the texts true and
the residual visible, not to close it.

**How the ratified entry was corrected.** `docs/decisions.md` `D-BB-BUILD-TAG` is owner-ratified, so
the false bullet is **left standing** and a dated `CORRECTION — 2026-09-05` bullet is appended
directly beneath it, in three parts: what the entry said, what is true (with the file:line chain),
and what follows (the residual, and the narrowing of the claim to the serve path). Rewriting ratified
text would have hidden that the error was ever made.

**The pin, because a comment would rot the same way.**
`TestR29aBondAuditStampsAWallClockNanosecondNotACounter` (`core/node`, **no build tag**, so it runs
in the required job) injects a clock parked at a real `walltime.Now()` reading, drives two real
`AuditBondsOnce` sweeps an hour apart through a recording ledger, and asserts three things: the tick
equals `uint64(clock.Now())+1`, it is of Unix-nanosecond magnitude, and the two ticks differ by the
elapsed **hour**. The third assertion is the discriminator that matters — magnitude alone passes for
a high-seeded counter.

| # | Revert | Result |
|---|---|---|
| c | the tick becomes a real request counter (`peAblCounter++`) | RED on the derivation arm (`tick = 1`) |
| d | the tick becomes a **high-seeded** counter, starting at the same wall-clock reading | RED on the DELTA arm only (`ticks 1 apart, want 3600000000000`) — arms 1 and 2 pass, which is why arm 3 exists |

`TestR29aBondChallengeStillStampsFirstSeenTick` also stops passing `tick = 77`, which made the value
look like a counter to every future reader (ruling C4), and gains a second-challenge arm pinning that
the stamp is FIRST touch and does not move.
