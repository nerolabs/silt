# 2026-09-05 — R2.11: a peer-submit path for a demand-issuer key registration

- **Date:** 2026-09-05 · **Seat:** BUILDER · **Branch:** `builder/r2.11-issuer-key-peer-submit`
- **Base:** `origin/main` = `492709c` (PR #746 merged)
- **Rock:** R2.11 · *"R0.4b-11 — no peer-submit path for an issuer-key registration. An attest-only
  validator's key is never committed. Fail-closed, liveness only."* Residual of the R0.4b-C3
  composed certification (`R0.4b-C3-composed-close-bc062d0-RESEARCH-CERTIFICATION-2026-09-03.md`,
  Residuals → Open).

**Context / trigger.** Under R0.4b a validator commits `(epoch, issuer) ↦ fingerprint(key_E)` to
consensus state so a redeemer can reject an off-commitment (targeted) demand key. The commitment
travels ONLY in a block the issuer itself proposes: `demandkeys.go` stages a signed
`IssuerKeyReg` in `n.pendingIssuerKeys`, and the proposer fold in `chainrole.go` folds the node's OWN staged
regs into its own proposal. A validator that never wins a proposal slot inside the registrable
window `[cur, cur+W]` (W = 4 epochs) therefore never commits its key: its demand tokens verify
against nothing, and the demand lane on it is fail-closed. The bond-renewal path had exactly this
problem (H2 / RT-2) and closed it with `MsgSubmitBondReg`: submit → validate-on-arrival → FIFO
queue → the designee folds. The entry mempool (#441) is the same shape. R2.11 is the third
instance of the pattern.

**Evidence (per build-immutable #7):**
- `core/node/chainrole.go:924-963` (at the merged head; `:888-926` on the base) — the proposer fold
  reads `n.pendingIssuerKeys` only (its own staged regs); nothing else feeds `b.IssuerKeys`. `core/node/demandkeys.go:105-141` — staging
  drops backdated regs and dedups per epoch; an attest-only node accumulates then drops W+1 regs
  per epoch forever (build-immutable #8 was already handled there).
- `core/chain/issuerkey.go:194-224` — the VALIDITY rules a block-carried reg must meet:
  era ≥ v5, `VerifyIssuerKeyReg` (self-signed, identity derived from `Pub`), epoch in
  `[cur, cur+4]`, issuer bonded when `MinBond > 0`. `IssuerKeyRegAdmissible` (`:352`) mirrors
  the bonded clause as proposer policy. **None of these change in R2.11.**
- `core/node/chainrole.go:439-490` — the `MsgSubmitBondReg` arrival gate, in order: per-sender
  rate budget BEFORE decode (`allowBondSubmit`, burst 8 per sync window; const `bondaudit.go:297`, func `:352`),
  `IsSlashed(from)`, decode, SENDER-BINDING (`ValidatorID() == from`, so a relayed third-party
  reg is refused before any verify), `ValidateBondRegErr`, then `queuePendingBondReg` (one slot
  per validator, latest wins, `maxMempool` cap). Every refusal LOGS (B5/#432: never refuse
  silently). Ack always OK.
- `core/node/objectivechain.go:81-122` — the submitter: only when renewal is DUE, self-signed,
  sent to every peer with a fire-and-forget ack; resubmits on the next sweep.
- `core/node/entrypool.go:33-45` — `entryEncode`/`entryDecode` ride the block-CBOR wrapper
  (`chain.Block{Entries: [e]}`) so a submitted payload travels without a new codec and
  version-checks like any block. `IssuerKeyReg` is already a CBOR block field (`b.IssuerKeys`).
- `ports/net.go` — the message-kind table (positional `uint8`; the new pair is APPENDED after
  `MsgDemandTokenReply`, landing at `:178-180`, never inserted beside `MsgSubmitBondReg` at
  `:144-146`), the name map, and the `IsReply` list a new pair must join.

**Options weighed:**
- **(A) Mirror `MsgSubmitBondReg` exactly — RECOMMENDED.** New kinds `MsgSubmitIssuerKeyReg`
  / `MsgSubmitIssuerKeyRegAck`. Payload: `chain.Block{Version, IssuerKeys: [r]}` encoded with
  `chain.Encode` (the entrypool shape; no new codec). Arrival gate, in the proven order:
  objective chain only; per-sender budget BEFORE decode (a NEW small budget, `issuerKeySubmitBurst`,
  because a reg costs one ed25519 verify — cheap — and should not share or drain the bond
  budget); `IsSlashed(from)`; decode; **sender-binding `r.IssuerID() == from`** (a relayed reg is
  refused before the verify); `VerifyIssuerKeyReg`; epoch window against OUR head
  (`r.Epoch ∈ [BlockEpoch(next), BlockEpoch(next)+W]` — the same clause `validateIssuerKeys` will
  apply, evaluated early so a stale reg never occupies a slot); already-committed → drop
  (append-only); then queue. Queue: `pendingPeerIssuerKeys`, ONE slot per (issuer, epoch),
  latest wins, capped at `maxMempool` — bounded by the bonded set × (W+1) in practice. Every
  refusal logs its reason. Proposer fold: after the node's own regs, append peer-submitted regs
  that are still in-window, not yet committed, and `IssuerKeyRegAdmissible` (**DROP otherwise —
  as built after the PE's S2(b); this draft said "defer", which is the C2 self-wedge discipline
  for our OWN reg and is unbounded retention for a peer's**), under the SAME v5 era gate; regs
  ride and stay queued until the chain confirms the commitment, then drop. Submitter: in the existing key-schedule sweep, a
  validator whose staged reg for an epoch is still uncommitted submits it to its peers (bounded:
  once per sweep per epoch, W+1 regs at most), like `SubmitBondRenewal`. Proposer POLICY and
  gossip only; **no validity rule moves** — an attester's acceptance of a block is untouched, so
  a mixed-version swarm cannot fork on it, and an old node simply drops the unknown kind.
- **(B) Piggyback on `MsgSubmitBondReg`'s payload** (a BondReg block wrapper already carries a
  `Block`; add `IssuerKeys` to it). Saves a message kind but couples a ~1.5 MB proof path to a
  ~150 B key path and its byte budget; a key reg would then wait behind the bond budget.
  Rejected.
- **(C) Gossip the reg to every validator so ANY proposer folds it, with no queue** — that is
  (A) without the queue; a reg that arrives between proposals is lost. Rejected.
- **(D) Have the chain accept a reg from a non-proposer as its own block content** — a validity
  change (I1 territory), research-gated, and not needed. Rejected.

**Decision + rationale:** (A). It is the tree's own settled pattern, twice built and
field-hardened (#424 rate gate, #432 loud refusals, #503 slashed-sender refusal, #286 byte
budget), applied to a payload that is small and cheap to verify. It changes no validity rule, so
it is not research-gated: the Researcher's residual asked for exactly this path and called it
liveness-only. A blind PE rules on the seam before code.

**Residuals, named:**
- Sender-binding means an issuer must reach at least one proposing peer itself; a validator
  that is partitioned from every proposer is still uncommitted (that is the network, not this
  mechanism).
- The peer queue is bounded by `maxMempool` slots keyed (issuer, epoch); a flood of fresh
  unbonded identities is refused before queueing when `MinBond > 0` (`IssuerKeyRegAdmissible`
  at fold; the bonded clause at arrival when the chain has a bond ledger), and by the per-sender
  budget otherwise.

**Gates planned (`core/node`, untagged):** the arrival gate refuses, in order and loudly, a
rate-exceeded sender, a slashed sender, an undecodable payload, a RELAYED reg (issuer ≠ sender),
a bad signature, a backdated or too-far-ahead epoch, an already-committed binding; a valid reg
is queued once per (issuer, epoch) with latest-wins; the proposer folds a peer-submitted reg
into a v5 block and drops it once committed; an attest-only validator's key reaches the chain
end-to-end in a two-validator sim where it never proposes; the kind pair is in the name map and
the reply list; `-tags bbootstrap` untouched.
