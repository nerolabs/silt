## 1. The mechanism, in one paragraph

An issuer honours the same publish credit twice **because** `creditSpent` (`core/node/node.go`, written at
`tokenrole.go` when a credit is converted into a demand token) is an in-memory map: a restart forgets every
spent credit, and a credit has no epoch in its FDH message (validity = the persisted publish key's lifetime),
so the durable `paidSerial` guard cannot catch the second token — it keys on the token serial and the attacker
holds two distinct tokens. Bound = credits held × issuer restarts; balance only, the γ→1/N firewall untouched;
live the moment the ledger persists or is shared. This change addresses that **by persisting `creditSpent`
behind the existing `ports.PaidSerialStore` port as a SECOND `guardstore.Disk` file (`creditspent.log`)** —
not a namespace in the paid-serial file, whose compaction evicts anything outside the ledger's live set —
appended BEFORE the credit is marked spent (the order already holds because `Issue` charges before it signs),
loaded at boot, capped, refuse-not-evict at the cap, under the R2.13 handle clause.

## 2. Options (from the ruling)

| Option | Verdict |

## 3. Shapes that are the Builder's
- A `creditspent.log` beside `paidserials.log` in the same store dir; opened at daemon start; the node holds
  it as a `ports.PaidSerialStore` (the record type is reused: epoch = 0 or the key epoch; serial = the credit
  serial). Load at boot into the map; `Append` before the in-memory mark; a store error refuses the withdrawal
  loudly (never issue on a credit the store could not record).
- Cap: same order as the paid-serial cap; at the cap, REFUSE new credits (never evict); no sweep (credits do
  not expire) — the cap's liveness face is disclosed, and the epoch-binding Rock is the structural close.
- The `tokenrole.go` comment "a signing failure does not burn the credit" is false (the ruling): correct it.
- Widen the Tester scar `scar-in-memory-guard-restart-hole` entry criterion (already done by the Tester).

## 4. Gates (RED-first)
G-CS-1 the PE's reproduction as a test: acquire a demand token with a credit, restart the issuer on the same
store, acquire again with the same credit ⇒ REFUSED (RED today: honoured). G-CS-2 a store `Append` failure
refuses the withdrawal and does not mark the credit spent in memory. G-CS-3 at the cap, a new credit is
refused and no existing record is evicted; a restart still refuses every recorded credit. G-CS-4 the handle
clause holds for the second file (the R2.13 shape: forced post-rename open failure ⇒ Append non-nil or visible).
