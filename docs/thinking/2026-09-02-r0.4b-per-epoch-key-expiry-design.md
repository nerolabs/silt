## 1. The break, attributed

`Ledger.RedeemDeliveryCredit` (`core/credit/delivery.go`) paid `fee − skim` on every call and
never saw the token serial. `demand.Bank.spent` is the double-spend guard, but it is
**per-server**: each server keeps its own bank. So K colluding servers sharing ONE demand token
(one blind withdrawal, one `ChargePublish`, one serial) each bank a self-named receipt and each
fire the conserved leg — minting exactly `(K−1)·fee`. That is the banned dual: a
network-minted per-receipt subsidy.

Evidence: `core/credit/open_break_cross_server_double_redeem_test.go` on the base pins the
`(K−1)·fee` mint as an OPEN break.

## 2. Why the bounded FIFO paid-serial guard alone was REFUTED

The obvious fix (dead branch `fcbab7e`, worktree `agent-a4a77944c919a67e4`) threads the serial
into `RedeemDeliveryCredit` and keeps a bounded FIFO `paidSerial` set. Its own doc-comment
claimed the eviction tail was safe because "evicting one guarded serial costs the attacker
`maxPaidSerial` other paid serials first."

The red-team refuted that claim, and the refutation is the reason this build exists: **each
flood serial is itself a paid delivery the colluding operator collects** — a net-neutral
self-payment — so advancing the FIFO by one window costs nothing and frees a WHOLE window of
already-paid serials for re-collection. The pump is self-financing. Staged gates:
`TestSerialGuard_EvictThenReRedeemMintsZero`, `TestSerialGuard_EvictionPumpIsNotSelfFinancing`.
Both are RED against a FIFO-alone guard while `TestSerialGuard_SetIsBounded` is GREEN — a triple
no FIFO-alone design can satisfy.

**The mechanism, stated once:** the FIFO guard forgets a serial that is *still redeemable*. The
fix is not a bigger cap. It is to make **forgotten ⇒ un-redeemable** true upstream, so eviction
can only ever touch a serial no honest path can still present.

## 4. The construction as built

**4.1 The epoch lives in the KEY, never in the token.** `Token{Serial,Sig}` and the signed
`receiptMsg = "silt/demand/receipt/v2" ‖ Serial ‖ Object ‖ Server ‖ Fetcher` are BYTE-IDENTICAL
to the base. The issuer blind-signs an epoch-E withdrawal under `key_E`; the epoch is DISCOVERED
at redeem by which held key verifies. The issuer keeps NO serial↔epoch map. Zero new receipt
quasi-identifier (cert Verdict 3).

**4.2 The window check.** `demand.Bank.Redeem` takes a `*demand.Keyset` (an epoch-indexed window
of issuer public keys) and the current epoch. It accepts iff some `key_E` in
`[current−W, current]` verifies — at most `W+1` RSA verifies. The verifier only HOLDS in-window
keys, so **the held keyset IS the window**; there is no arithmetic on a token field to forge.

**4.3 W = 4 epochs, an Evolving-tier knob, epoch-denominated.** `demand.DefaultWindow = 4`,
`DerivedEpochBlocks`-denominated, resolved from the consensus epoch clock
(`head_height / EpochBlocks`) — **never wall-clock**. Block time in silt is emergent, so an
epoch-denominated window auto-scales with the swarm's real cadence (economist §2). The VALUE is
assumption-based (the honest serve→bank latency tail is unmeasured, cert residual R0.4b-2); the
sim that confirms it is named in the economist advisory §5 and is owed to the Tester.

**4.4 The consensus-attested `E ↦ key_E` binding.** A new committed keyspace
`issuerKeyCommit: epoch → (issuer NodeID → fingerprint)`, where the fingerprint is
`sha256(MarshalPub(key_E))`. Written by a new additive block field `IssuerKeys []IssuerKeyReg`.
A redeemer resolves `key_E` against this committed binding and REFUSES an off-commitment key.
That is the mandatory anti-fingerprinting mitigation (cert Verdict 2), not an optional hardening.

**4.5 Credit-layer expiry visibility (R0.4b-3, the coupling condition).**
`RedeemDeliveryCredit` takes the serial AND its issuing epoch AND the current epoch. The
`paidSerial` guard evicts **BY EXPIRY ONLY**. See §6 — this is the load-bearing build call.

## 5. The committed-format addition — the STOP condition, checked

The cert's Verdict 2 makes this an immutable-F committed-format change and an owner veto-gate.
The routing constrains its SHAPE: *an ADDITIVE leaf appended to the open-era state-root leaves,
the same shape as the F1 whole-set digest-root additions — append only, existing leaves
untouched, era-3 (frozen) root byte-identical.* **STOP and report if the binding cannot be an
append-only leaf.**

**Checked. No STOP condition hit.** Concretely:

- New tag `issuerKey\x00`, emitted **only** by `stateRootLeavesV5` (the open era). The era-3
  marshaller `stateRootLeaves` is untouched, so a v4 block's root stays byte-identical to era-3.
  Pinned by the existing `TestEra3RootByteIdenticalWithV5KeyspacesPresent` (extended to populate
  the new keyspace) — exactly the guard the F1 digest roots ride.
- **No existing committed field changes.** No existing leaf's key, value, encoding, or emission
  moves. The addition is a new keyspace and a new `omitempty` block field; a block with no
  `IssuerKeys` hashes exactly as before (the same additive discipline `BondRegs` and `Slashes`
  already ship).
- `IssuerKeys` are **valid only in a v5 block**. A v4 block carrying them is rejected. Without
  that gate a v4 block could write committed state the era-3 leaf set does not cover — a silent
  divergence. This is the one rule the addition adds, and it exists to PROTECT the freeze.

**Leaf shape call (deviation from a literal reading, disclosed).** F1 commits *one scalar leaf
per keyspace whose value is an MTH over the canonical member list*. Here the binding is emitted
as **per-member leaves** (`issuerKey\x00 ‖ uint64BE(epoch) ‖ issuerID`, value = the 32-byte
fingerprint), the `bondRootOwner` shape — NOT an MTH scalar. Reason: F1's MTH scalars exist so a
**root-only floor box can prove SET COMPLETENESS of a whole-set fold**. Nothing folds this
keyspace: no validity predicate, no quorum, no fork-choice, no recompute reads it. A redeemer
resolves ONE `(epoch, issuer)` leaf, which a per-member inclusion proof answers directly and an
MTH scalar would not. Adding an inert digest root with no reader is machinery with no
justification. **Reopening condition:** if a root-only recompute ever folds this keyspace, it
needs an `issuerKeyRoot` digest leaf added to `stateRootDigestTagsV5` before it can prove
completeness. Recorded here so the obligation is not lost.

**Floor-box recompute.** The keyspace is INERT to consensus, the same STOP boundary F1 declared.
A v5 block carrying `IssuerKeys` is OUT of the O(payload) recompute's scope, so
`stateRootScopeGate` gains an explicit clause that **STALLS** on it. Without the clause the box
would still stall — the un-named leaf write diverges the folded root from the committed root, so
it lands on `ErrRecomputeStateRootMismatch` — but it would stall with a misleading "forged root"
error. The explicit clause makes the stall named and honest. **The box never-Accepts either way.**

## 6. The load-bearing build call: eviction is EXPIRY-ONLY, and at cap we REFUSE TO PAY

This is the decision the two red-team gates actually turn on, so it is stated in full.

The cert's coupling condition (Verdict 1) is: *"evicted ⇒ expired" holds ONLY if the credit-layer
prune predicate is keyed on the serial's issuing epoch leaving the window.* Realized literally:

```
sweep: drop every paidSerial entry with  issuedEpoch + W < currentEpoch
```

An entry dropped by that sweep is, by construction, one the demand layer will now REJECT at
`Redeem` ("token expired or not issued") before any credit path — no `key_E` verifies it. The
evicted set and the expired set are the SAME set. That is the composed property (b)-prunable
needs.

**What happens at the cap when nothing is expired?** Two candidates:

- *Fall back to FIFO.* REJECTED. This reinstates exactly the refuted design: it forgets a
  still-redeemable serial, and both red-team gates go RED again. The gates are not a formality —
  they are the discriminator between this design and the refuted one.
- *Refuse to pay (return 0).* **CHOSEN.** No serial is ever forgotten while it is still
  redeemable. Conservation is absolute: the guard can only ever cause an UNDER-pay, never an
  over-pay and never a mint — the same "give" the A4 eviction fix already accepts and the same
  direction rule (b) allows ("one delivery, one payment" bounds above, not below).

Reaching that state requires a serve rate above the modeled bound, and it self-heals one epoch
later as the sweep frees slots. The cap exists as a **safety bound on floor-box state
(build-immutable #8), not a rate limiter** — the economist's §3 conclusion, taken literally.

**The cap is DERIVED, not a bare constant** (economist R-ECON-2 — "keeping `8192` alongside a
4-epoch window is the one combination to AVOID"):

```
maxPaidSerial = max(65_536, W × EpochBlocks × maxServeTrackedPerBlock)
              = max(65_536, 4 × 8 × 256) = 65_536
```

At ~90 B/serial that is ~5.6 MB — three orders of magnitude inside the 2 GB floor box
(economist §3). The floor of 65,536 is what makes the cap DOMINATE the honest live set, which is
the property that keeps expiry — not the cap — doing the eviction work.

## 7. Deviation from the routing's literal wording, and why (disclosed for review)

The routing says to make `MsgGetIssuerKey` / `answerIssuerKey` / `peerIssuerKeys` epoch-plural.
The cert's grounded picture names the same three symbols as the demand lane's key path.

**Verified against source, that identification is wrong, and following it literally would be a
consensus break.** `MsgGetIssuerKey` serves `n.issuerKeyDER`, the **PUBLISH-token** issuer key
(`core/node/tokenrole.go`). `IssuerKeyOf` is wired as the chain's `issuerKey` lookup
(`chain.RequireTokens`, `chain.go:2121`), and `publishtoken.Verify` re-verifies **committed**
publish tokens against it on every replay (`chain.go:2621`). Rotating that key per epoch would
make historical committed publish tokens fail verification on replay — a consensus break, and a
direct hit on the frozen era-3 rules.

Demand withdrawal reuses that same key today only because RSA-FDH signing is domain-agnostic:
`answerTokenRequest` cannot tell a demand blind from a publish blind, since the blinded value is
opaque (the domain lives in the FDH message the *requester* built).

**So the per-epoch keyset is a SEPARATE demand-lane keyset**, and the issuer must be TOLD which
lane it is signing for. Built as the routing's mechanism on a parallel wire:

- `MsgGetDemandIssuerKeys` / `MsgDemandIssuerKeysReply` — serve/fetch the window
  `{key_E : current−W ≤ E ≤ current}`.
- `MsgDemandTokenRequest` / `MsgDemandTokenReply` — blind-sign under `key_current`; the reply
  carries the epoch in `Message.Height`.
- `n.peerDemandKeys` — the cached, PINNED keyset, cross-checked against the committed binding.

This delivers exactly what the cert requires (serve, fetch, cache, pin a WINDOW; resolve `key_E`
against committed state) without rotating a key the frozen consensus rules depend on. The
publish-token lane is untouched. **Flagged for the reviewing seats as a deliberate deviation.**

## 8. What is NOT built (scope, disclosed)

- **Automatic per-epoch RSA keygen scheduling in the daemon.** The node exposes
  `SetDemandIssuerKey(epoch, key)` and prunes to the window; *when* an operator rotates is ops
  policy. This is cert residual **R5 (MINOR, build)** and it does not gate any of the six
  acceptance gates.
- **The W-value measurement.** Cert residual **R0.4b-2**, owed to the Tester (economist §5 names
  the sim). W = 4 ships as the certified-construction default, not as a measured value.
- **The cross-owner-ledger variant.** K truly distinct-owner ledgers do not share a `paidSerial`
  set. That remains the standing Douceur / demand-authenticity limit, neutralized today only by
  the γ→1/N firewall. Unchanged by this build, disclosed here so it is not read as closed.

## 9. Firewall and conservation, re-checked

- **γ→1/N firewall untouched.** Every field this build adds lives in the balance economy or in a
  committed keyspace no standing predicate reads. `Redeem` never touches standing; expiry only
  ever REJECTS a redemption, and a rejected redeem credits zero. Structurally asserted by the
  existing `TestInvariantA_*` guards, which stay green.
- **Nothing is minted.** Expiry and the paid-serial guard are purely subtractive on the
  redemption side. Conservation `#receipts(C) ≤ #issued-tokens-spent` is preserved a fortiori: a
  narrower acceptance set cannot exceed the issued-token bound.
