## 1. The mechanism, in one paragraph

The failure is a **cross-server double-redeem** that re-opens whenever one RSA key is bound
to more than one epoch, **because** `issuedEpoch(token)` was a function of the token AND the
verifier's current keyset: `VerifyInWindow` returned the newest held epoch whose key
verified, so a token withdrawn at epoch 0 under key K was re-dated to epoch 3 once K was
also registered for 3 — which an ordinary restart does. The credit guard tags its entry with
the epoch the redeem reported and sweeps at `E + W`, so entries expired while tokens did not,
and a second server on the same ledger collected a second full payout per serial. This change
addresses that **by binding the issue epoch into the blind-signed message**, so a signature
verifies under exactly the pair `(key_E, E)` and `issuedEpoch` becomes a pure function of the
token for any key schedule. Evidence: red-team probes G and I (both passing against the
pre-fix tree); the gates below are those probes inverted, and each goes RED again when the
binding is removed.

## 2. (b1) — the encoding, and why this one

`fullDomainHashD` already took (public key, message, domain). The demand lane now passes
`epoch(8B big-endian) ‖ serial` as the message, under a **v2 domain**:

```
demand FDH input = H("silt/blinddemand/fdh/v2" ‖ ctr(4B BE) ‖ epoch(8B BE) ‖ serial), counter mode
```

Choices, each deliberate:

- **Big-endian, 8 bytes.** Every other epoch encoding in the tree is already this
  (`chain.issuerKeyRegMsg`, the `issuerKeyCommit` leaf key, `demandDedupKey`). One epoch wire
  form, not two.
- **A new domain (v2), not an extension of v1.** A v1 (unbound) demand signature must never
  verify as a v2 one. Retiring the domain makes that structural rather than a review
  obligation. Cost: outstanding demand tokens do not survive the upgrade. They have a
  W-epoch life by construction and the lane is not live on any network (era-4 has never
  locked in — §7 of the verdict), so the cost is zero and the alternative is a compatibility
  shim that would exist forever.
- **Publish and credit domains are untouched, byte-for-byte.** Committed publish tokens are
  re-verified on every chain replay; a change there would invalidate history.
  `TestPublishAndCreditFDHAreUnchanged` recomputes both independently.
- **Not a token field.** An explicit issue-epoch field on `Token` carries the same
  information at the price of a wire change. `Token{Serial, Sig}` and `receiptMsg` are
  byte-identical to the pre-R0.4b shape, so no new receipt quasi-identifier exists (the R0.4
  Q1 refutation is of a WALL-CLOCK stamp; this is a consensus epoch index, certified
  Q1-neutral).

**Wire impact: the request names `E` in `Message.Height`, and nothing else changes.** That
field already exists and already crosses the wire (`adapters/tcpnet/wire.go` cbor 15); the
reply already carried the epoch. The STOP condition ("(b1) needs a wire change beyond naming
E") was not reached.

**Issuer admission rules** (`answerDemandTokenRequest`): sign under `key_E` iff `E <= cur`,
`cur − E <= W`, and `key_E` is held. Signing for a FUTURE epoch is refused even though the
pre-published key exists — it would hand out a token that outlives the honest window. Naming
an earlier `E` only shortens the requester's own token, so there is nothing to police below
the window. This is also what closes the epoch-boundary race (R0.4b-7): a requester whose
clock trails by one epoch names that epoch and the issuer, which retains the window's private
keys, signs for it.

## 3. The rotation and store shape (my call)

### 3.1 What must be true

- The lane can issue only for an epoch whose key is **held** and **committed**, so something
  must be registered every epoch, pre-published up to W ahead (the chain's registration
  window).
- The **publish key must never enter the demand keyset**. It cannot rotate — committed
  publish tokens re-verify against it — so using it as a per-epoch key gave the lane a life
  of exactly W+1 epochs while the fee-charging path kept charging.
- A restart must return the SAME keys for epochs whose fingerprints are already committed.
  The binding is append-only and backdating is rejected, so a regenerated key can never be
  registered: the lane would be dead for a whole window with no recovery.

### 3.2 The band: `[cur − W, cur + W]`, generated forward only

Retain back to `cur − W` (the private key for an in-window past epoch must still sign — the
boundary race); pre-publish forward to `cur + W` (so `key_E` is committed before epoch E
opens). A fresh node generates only `[cur, cur + W]`: generating the past band too would cost
W extra RSA keygens at boot for keys nothing was ever issued under. Steady state is one
keygen per epoch; first boot is W+1.

### 3.3 The store: ONE file, CBOR map `epoch → PKCS#1 DER`, atomic temp+rename

`adapters/diskissuer.EpochStore`, beside the existing publish-key `Store` — same concern,
same directory root, so the mechanism is extended rather than duplicated.

Alternatives refused:

| Shape | Why not |
|---|---|
| **One file per epoch** | Better containment (a corrupt file loses one epoch) but it costs a filename codec, a directory scan, and a per-file corrupt-or-absent decision at every load. The band is ≤ 2W+1 ≈ 9 keys ≈ 11 KB; there is nothing to page. Both layouts sit on one disk in one directory, so the containment gain is thin. |
| **Derive `key_E` from one persisted seed** (HKDF → deterministic keygen) | Tempting: one secret, no pruning, no round-trip. **REFUTED.** `crypto/rsa.GenerateKey` is explicitly not stable across Go versions, so a toolchain upgrade would silently regenerate different keys for epochs whose fingerprints are ALREADY COMMITTED — an unrecoverable liveness cliff (append-only, no backdating) bought for a few KB. |
| **Reuse the publish key store** | It is the exact thing C3 forbids. |

A corrupt store is a hard error, never a silent regeneration: quietly minting new keys over
committed fingerprints is unrecoverable; refusing to start is not.

### 3.4 The scheduler

`EpochStore.RotateWindow(rng, cur, w, install)` does the band arithmetic and calls back per
key. The daemon binds it to silt's W in exactly one place (`installDemandKeys`), drives it at
boot synchronously (the lane must not be dark for the first commits), and on every epoch turn
from the commit stream. **Keygen and the disk write run OFF the node loop** — an RSA-2048
keygen is hundreds of milliseconds and the loop is single-threaded — with only the installs
posted back. One rotation is in flight at a time because the epoch watermark is bumped on the
loop before the goroutine starts.

The same `RotateWindow` is what the node-layer lane-lifetime gate drives, so a drift between
the daemon's schedule and the gate's is not possible.

## 4. The other four fixes, briefly

- **Stale registration → proposer policy.** The fold drops a pending reg with
  `Epoch < blockEpoch(next)` and the scheduler re-stages. Never validity: an attester's
  acceptance rule is untouched, so a mixed swarm cannot fork on it. `SetDemandIssuerKey` also
  refuses to stage a backdated reg and prunes the staged queue, which additionally closes an
  unbounded-growth path (W+1 dead regs per epoch on a node that never proposes —
  build-immutable #8).
- **The pin follows the chain.** `DemandIssuerKeyset` re-validates every held key against the
  current commitment on read (≤ W+1 sha256, negligible next to the RSA verify the read exists
  to do), and `pinDemandIssuerKey` re-points on mismatch. Read-time was chosen over
  invalidate-on-`EnableChain`/reorg because it has no hook to forget: every adoption path is
  covered by construction.
- **Shipped lanes on the pinned keyset.** `swarm receipt` uses `FetchDemandIssuerKeys` +
  `AcquireDemandTokenInWindow`; the D3 client takes `(key, epoch)` resolved by the durable
  parent (`Node.ResolvedDemandIssuerKey`) and withdraws on `MsgDemandTokenRequest`, failing
  on `Height != E`. The unpinned `AcquireDemandToken` is **deleted** rather than deprecated —
  it had no safe calling convention. `AcquireDemandTokenWithCredit` moved off the legacy
  publish lane, which is the "migrate, don't half-refuse" the verdict requires.
- **Rollout gate.** `TestReadinessStampImpliesIssuerKeyCoverage` asserts hash coverage of
  cbor 17 and `issuerKeyCommit` in the v5 leaf set unconditionally (a vacuous gate protects
  nothing) and logs loudly if the readiness stamp is ever raised. The stamp is NOT raised
  here.

## 5. Observability (my call)

The Tester measured that a cap-full refusal returned a bare `0`, indistinguishable from
self-delivery, an already-paid serial, or a zero fee — and surfaced at the node inside a line
reading `delivery receipt banked`, which is actively misleading.

Shape chosen: `RedeemDeliveryCreditReason` returns `(int64, string)` alongside the unchanged
`RedeemDeliveryCredit`, plus two monotone counters (`GuardFullRefusals`, `SerialSweeps`). A
**string, not a typed enum**, because the value is log output: it keeps the optional
ports-side interface free of a `core/credit` type and keeps the log line and the test
assertion the same literal. The values are an announced observable contract (S5).

The `delivery receipt banked` line is **unchanged** (S5: never move a marker other tests
watch). A banked receipt that settled nothing now gets its OWN line, at WARN, naming the
reason and the counter — deliberately not using the word "banked".

**Sweep at most once per epoch** (RT-E). Nothing can expire twice within one epoch, so the
swept set is identical and the amortized cost drops from O(cap) per refused redeem to O(cap)
per epoch. Purely a cost fix.

A second blind red-team pass on the C3 close

confirmed **ten breaks and two refutations**. The (b1) epoch binding itself held under
every attack; the breaks are in the machinery around it. Every probe was re-run against

### F1 — CRITICAL (latent). Floor-box vs full-node split at every epoch turn

**Root cause.** `applyIssuerKeys` called `pruneIssuerKeyCommit(b.Height)` on EVERY v5
apply, so a block carrying ZERO registrations still deleted committed `issuerKeyCommit`
leaves at the epoch turn. The floor box's scope gate stalls only on
`len(b.IssuerKeys) > 0` and its O(payload) fold has no op for the prune, so those
committed writes were neither folded nor named. Measured both ways: the box AGREED with
a forged root the full node rejects, and read an HONEST zero-registration block as a
forged root. Latent today only because `WitnessValidateV5` never returns Accept; a
wrong-Accept the moment R1.8 flips the box.

**The close, and why it is neither of the two closes the routing named.**

- The FAITHFUL close (the fold reproduces the prune from committed data) is
  **unavailable**. The prune is a pure function of the pre-state leaves and `b.Height`,
  but the box does not HAVE the pre-state leaves — it has a root and an untrusted
  witness, and `core/statehash` offers point membership/non-membership only. There is
  no range proof and `issuerKeyCommit` carries no set-completeness digest leaf. A
  witness-supplied member list is omission-forgeable, and an omitted doomed leaf is
  exactly the wrong-Accept again. (`dueBucket`'s committed MTH is what makes class T's
  height-driven sweep witnessable; `issuerKeyCommit` has no counterpart, and adding one
  is new committed state.)
- The CONSERVATIVE close (stall whenever a prune could fire) is sound but the only
  predicate the box can evaluate soundly is "this height advances the epoch" — it
  cannot ask whether any `issuerKeyCommit` leaf exists without enumerating. That stalls
  **every boundary block, forever**, which is where class P (rotate) lives; it trades a
  permanent hole in the box's coverage for an apply()-side scan that has no reason to be
  height-driven.
- **Shipped instead: the prune is PAYLOAD-DRIVEN.** `pruneIssuerKeyCommit` now runs only
  inside the registration-carrying branch of `applyIssuerKeys`. A block with no
  registrations writes nothing in the keyspace, not even a delete, so
  "`len(b.IssuerKeys) == 0` ⇒ no `issuerKeyCommit` write" becomes a property of apply()
  rather than an assumption of the box, and the leaf-diff exemption's word "only"
  becomes true. Build-immutable #8 is untouched: every ADD is in-band by validity
  (`cur <= e <= cur+prePublish`), so pruning at each add re-establishes the 2W+2-bucket
  bound on every block that can grow the keyspace; a run of registration-free blocks
  cannot grow it. Nothing reads the band — the demand keyset's own window decides what a
  token verifies against, and `validateIssuerKeys` already rejects a backdated epoch —
  so a leaf that outlives the band is unreachable, not authoritative.

**This is a consensus-rule change and it is UNCERTIFIED.** It changes the committed root
of any v5 block at an epoch turn over a non-empty `issuerKeyCommit` keyspace. It is
available cheaply only because the whole keyspace is new on this unmerged branch. It
must be certified before merge.

**Gates.** `core/chain/rt_r04b_c3_split_test.go` drives the exact red-team scenario
through `eachTier` — the box recompute, the LIVE `validateEra3Roots`, and
`WitnessValidateV5` as both a cold auditor and a live follower — in both directions
(forged root the full node rejects; honest root the full node accepts) and asserts the
tiers never disagree and the box never Accepts. Plus
`rt_r04b_c3_prune_test.go` (payload-only writes, the bound over 100 blocks),
`rt_r04b_c3_prune_accept_test.go` (the forged pruned root is refused), and
`TestLeafDiff_IssuerKeyCommitIsPayloadOnly`, which earns the exemption's "only" across
12 epoch turns. All six go RED under a one-line ablation restoring the unconditional
prune.

### F2 — the guards' memory was weaker than the token's validity

**Root cause.** Both guards were process memory with no persistence and no restore, so a
restart evicted EVERY serial, in-window or not, and the identical `MsgDeliveryReceipt`
was banked and paid twice.

**Fix.** A durable, ordered guard: `ports.PaidSerialStore` + `adapters/guardstore` (an
append-only log of fixed-width records, fsync per append, atomic temp+fsync+rename+
dir-fsync on compaction — the `markstore`/`diskissuer` shape). The ledger appends BEFORE
any credit moves, so a crash leaves a guard entry for a payout that never happened (an
under-pay) and never the reverse; a store that cannot write refuses the payout
(`ReasonGuardStore`); a redeem before the load completes is refused
(`ReasonGuardUnloaded`), not paid. The daemon opens and loads it before the node exists.

**Scope, stated plainly.** The CREDIT guard is persisted — that is the money leg, and it
is what makes the second presentation pay 0. `demand.Bank.spent` is NOT persisted: it
gates a neutral observable (`Bank.Demand`) that no rule reads, and on every shipped path
the ledger is downstream of it, so a bank that forgets across a restart re-counts a
delivery but cannot re-pay one. Flagged for the Researcher in case the coupling
condition is to be restated over both.

### F3 — "evicted ⇒ expired" was false in-process

**Root cause.** `paidSerial` was keyed by the SERIAL ALONE while the sweep epoch was
whatever the FIRST redeem supplied — the MINIMUM epoch over the tokens sharing a serial.
The withdrawer picks both the serial and the epoch, so the low-epoch entry expired and
the guard forgot a serial for which a still-in-window token existed.

**Fix.** Both guards are keyed by the TOKEN: `uint64BE(issueEpoch) ‖ serial`. An entry is
removed only once ITS OWN issue epoch is outside the band. The pump is unaffected — the
same token at two servers is one key either way, and a second token on one serial costs a
second withdrawal fee — and the invariant is restated per token, which is what it always
should have been.

### F4 — a committed RSA key was never validated

**Root cause.** The consensus commitment attests `sha256(MarshalPub(key))`: 32 bytes.
That binds WHICH BYTES an issuer serves and says nothing about whether they are an RSA
key. `N = 0` panicked every verifier inside `big.Int.Mod`; `N = 1` verified every
`(serial, sig)` pair; `E = 1` made the signature the message.

**Fix.** `blindtoken.ValidatePub` is the single definition of well-formedness — N odd,
positive, `[2048, 8192]` bits; E odd, `> 1`, `<= 2^32-1` — enforced at `ParsePub` (the
wire), at `Keyset.Put` (the door), and defensively before every modexp. Note for the
record: there is nothing to validate at the chain's registration fold, because the
committed leaf is a hash, not a key; "commit time" for this lane is the moment a key
enters a keyset.

### F5 — `demand.Bank.spent` was unbounded, and no guard bounded the serial's SIZE

**Fix.** `spent` is capped (derived the same way the credit cap is) and expiry-swept on
the token window, refusing rather than evicting at the cap; `demand` and `credited` are
capped by object count. The serial is bounded at the wire decode
(`UnmarshalSubmittedReceipt`, together with the token signature and the receipt's
ed25519 fields) and again at `Bank.Redeem`, so no attacker-chosen byte count can become
a long-lived map key.

### F6 — `EpochStore` had no lock

**Fix.** A mutex spanning the whole load→generate→save cycle, with `install` called
outside it (holding a store lock across a caller-supplied callback that posts to the
node loop is how a rotation deadlocks). The gate asserts the OUTCOME — no installed key
is ever absent from the store — because `-race` cannot see this: each goroutine's `Load`
builds its own map, so the corruption is a file-level lost update, not a memory race.
Ablating the lock reddens it 3/3.

### F7 — one corrupt byte bricked the whole validator

**Fix.** The daemon reads the demand key store before arming the lane and degrades to
**lane-off**, loudly, on a read failure; chain, storage and serving continue. The file is
never rewritten or regenerated on that path — quietly minting new keys over
already-committed fingerprints is the unrecoverable failure (F6's cliff), so a corrupt
store is left exactly as found for an operator to restore.

### F8 — the monotone epoch watermark is a one-call permanent denial: NOT FIXED HERE

`epochWatermark` is raised from a caller-supplied `currentEpoch` with no bound and never
falls, so one `currentEpoch = 2^62` call refuses every subsequent honest redeem forever.
Bounding it requires deciding what the ledger may trust about a redeemer's clock, and at
the shared-ledger boundary R0.4b-5 exists for, that boundary is **not authenticated at
all** (`RedeemDeliveryCreditReason` credits `fee − skim` there with no debit and no proof
a fee was collected). The red-team routed the underlying question to the Researcher —
does R0.4b-5 buy anything in its own threat model? — and it is a mechanism choice, not a
patch. **Left open, deliberately.** Unreachable on the shipped per-node topology, where
`currentEpoch` is the node's own head and the finality gate forbids it decreasing.

### F9 — gate F asserted the fork condition and never failed on the stamp

**Fix.** Clause (c) is a hard failure via the factored `gateFStampPin`, and
`TestGateF_StampRaiseIsAHardFailure` proves the tripwire has teeth without raising the
real constant. `TestGateF_ConfigActivationRouteCarriesTheSameCoverage` covers the OTHER
route to v5 — `Config.Era4ActivationHeight`, which activates era-4 with no readiness
signalling — by driving a config-activated chain end to end and asserting the same two
coverage properties on a real minted block.

Already held-in-tension in §7. The number is now pinned by

### G-3 — a torn tail was not realigned at `Open`

**Root cause.** `guardstore.Open` opened `O_CREATE|O_WRONLY|O_APPEND` with no size
check. `Load` drops a trailing partial record, which is sound only while the partial
record *stays* the tail. `O_APPEND` sets the write offset to the file's size, so after a
crash mid-`Append` the next append landed at an UNALIGNED offset and shifted every
record boundary after it. The following `Load` spliced the orphan fragment onto the head
of the real record: with an impossible spliced length byte the store is a refuse-to-start
outage, and with a plausible one (~1 in 8) the load succeeds SILENTLY with wrong contents
and an **acknowledged paid serial is no longer guarded**. That is the F2 double-pay,
through the adapter written to close F2.

**Fix.** `realign(path)` runs inside `Open`, before any append handle exists: stat,
truncate back to `size − size%recSize`, fsync. Dropping the fragment is safe by this
store's own argument — a partial record means `Append` had not returned, so the ledger
had not moved credit against it. The fsync is what makes the shorter size durable BEFORE
an append can be written past it.

**Gate.** `adapters/guardstore.TestTornTailIsRealignedBeforeTheNextAppend` — write 3
records, append half a real record, reopen, append one more, reopen, and require all four
entries byte-exact plus an aligned file size. RED before the fix and RED under ablation
(entry 3 read back as a splice with the acknowledged serial absent);
`TestTornTailIsDroppedNotFatal` still passes, since it never reopens.

### G-4 — every guard refusal returned before the supersede

**Root cause.** Five refusal paths returned above the supersede block, so a REFUSING

profitable, operator-triggerable **supersede-disable** on the whole of Boulder 0's
conservation rule.

**Fix — the ordering the certification allows, not the naive one.** The naive "run the
supersede before every refusal" is REFUTED: the lane key is `(server, requester, root)` —
a lane, not a delivery — so a receipt cannot say which serve it acknowledges, and
`ReasonAlreadyPaid` is what stops a re-presented receipt from reversing a RE-SERVED
lane's fresh self-mint (RT-DELIV-1/1b/2). The shipped order is therefore:

1. `ReasonSelfDelivery`, then `ReasonAlreadyPaid` — above the supersede, no reversal.
2. The supersede — reverse the serve's self-mint, delete the lane.
3. `ReasonGuardUnloaded`, `ReasonBackdated`, `ReasonGuardFull`, `ReasonNoFee`,
   `ReasonGuardStore` — below it. Each pays 0 and no longer keeps the mint.

Stated in the code as: **a witnessed receipt reverses the self-mint exactly once,
whether or not it is paid.** "Exactly once" is bounded by the lane deletion, and
"witnessed" by the bank: an unwitnessed or malformed receipt returns `credited=false` at
`core/node/demandrole.go` and never reaches the ledger, so the self-mint stays until a
valid receipt arrives — the unwitnessed bilateral fallback, unchanged.

The accepted give is the certification's: a restart-gated, **subtractive** revenue-grief
(re-present in-window receipts against freshly served lanes) in exchange for removing a
mint-preserving lever. That is the right side of the priority order — a reversal is an
under-pay, never a mint.

**Root cause NOT closed.** R-FLAT-FEE — the flat conserved leg against the
byte-proportional self-mint — is what makes *any* refusal path a profit lever. Fixing it
is a D-POD-KNOBS re-pricing (size-denominated fee, or one token per chunk) and needs its
own certification.

### F6 — an earlier rotation pruned a later rotation's pre-published key

**Root cause.** `ensureBand` pruned on the CALLER'S OWN band (`e > genTo`, `genTo = cur+w`).
The daemon launches each epoch turn as a bare `go rotateDemandKeys(cur)`, so turns complete
out of order, and a turn for an EARLIER `cur` deleted keys a LATER turn had already
generated **and handed to `install(...)`**, which stages their fingerprints on chain.
`applyIssuerKeys` is first-write-wins, so once a staged fingerprint commits the regenerated
key can never be registered: the lane is dead for that epoch, for that issuer, permanently.
Measured with no concurrency at all — `RotateWindow(11)` to completion, then
`RotateWindow(10)`, loses epoch 15.

The EpochStore mutex (the previous round's fix) closed a different, memory-level mechanism
and left this one live.

**Fix** (`adapters/diskissuer/epochkeys.go`). The retained band's upper edge is
`max(genTo, highest epoch already on disk)`. It only ever grows, so no rotation can shrink
another's pre-publication. It stays bounded because the only writer above the edge is the
generation loop, which stops at `cur+w`. The LOWER edge deliberately stays the caller's
`keepFrom`: dropping a past-epoch key is the intended drain, and an out-of-order earlier
turn can only widen it.

**Gates** (`adapters/diskissuer/rt_r04b_c3_store_test.go`).
`TestRTC3_AnEarlierRotationDoesNotPruneALaterRotationsPrePublishedKey` — the deterministic
sequence, no goroutines; RED before the fix with `LOST=[15]`.
`TestRTC3_EpochStoreRotationsNeverLoseAnInstalledKey` — the daemon's four overlapping turns,
**80 attempts** (5 under `-short`); RED before the fix with `LOST=[17]`.

**The adopted gate's `if e < 9 || e > 14 { continue }` filter is removed**, and the
assertion is now unconditional. The filter's rationale had the direction backwards (the
pruning turn is the earlier one) and it carved out the only epoch ever lost. Why the
unfiltered assertion is sound is written into the test rather than left implicit:
generation starts at `genFrom = cur`, so the lowest epoch any turn creates is
`min(cur) = 10`, while the highest lower prune edge any turn uses is `max(cur) − w = 9`.
9 < 10, so the legitimate lower-edge drain cannot reach a key this topology installed.

**A false comment removed** (`cmd/silt/daemon.go`): "one rotation is in flight at a time
because `demandEpoch` is bumped here" was wrong. Bumping `demandEpoch` prevents a duplicate
rotation for the SAME epoch and does nothing about concurrent rotations for DIFFERENT
epochs, which is the case that lost a key.

### The PE's remaining items

**H-2 — `rotateDemandKeys` armed on a LANE OFF branch.** Fixed by ORDER, not by a
compensating `= nil`: the single assignment now sits BELOW the boot install's single
failure exit, so no branch is left that can arm a lane it has just declared off. Gated by

**H-3 — the guard store's refuse-to-start bricked lane-less nodes.** `guardstore.Open` +

neither can be greened by deleting the other.

### Main-side finding, recorded not fixed

A bare `go test ./...` has no margin against Go's 10-minute default package timeout in
`core/chain`. Measured on this tree, 2026-09-03: `TestMeasureRecomputeMatureNowStreamingWin`
alone **309 s**, the whole `core/chain` package **530 s** with an explicit `-timeout 40m`. On
`origin/main` `2247235` it was reported timing out outright (~7.5 min for the same test on
that run), so which side of the limit a given machine lands on is decided by load.
It is a MEASUREMENT test with an always-on fast structural twin, and it is skipped under
`-short` (which CI uses), so nothing is broken — but the documented full-suite command
needs an explicit `-timeout`. Filed as a ROADMAP residual; the test is NOT changed here,
because it is not this branch's and changing another branch's measurement under a
receipt-expiry commit is how a regression hides.
